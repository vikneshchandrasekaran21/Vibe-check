# Internationalisation and localisation

Load this file when the app supports more than one language or region, sells to several countries, or targets users whose language isn't English. Translation gaps and wrong formats look broken to users, and in some places (e.g. Quebec) missing language versions are a legal problem (see `lawsuits.md`).

## Language
- [ ] 🔴 LOC-001 **No missing translations:** every visible string in each supported language, including errors, emails, notifications, buttons, empty states, legal pages and app store listings. No raw keys like `checkout.button.pay` or mixed languages on one screen.
- [ ] 🔴 LOC-002 **Legal and consent text in each language users get,** and the translations say the same thing as the original (privacy policy, terms, consent banner, parental consent).
- [ ] 🟡 LOC-003 **Strings aren't hard-coded** in components. They come from translation files, so new languages can be added.
- [ ] 🟡 LOC-004 **Plurals and grammar handled properly** (ICU message format or the library's plural rules), not `count + " items"`.
- [ ] 🟡 LOC-005 **Language selection:** detected sensibly (browser or device language), changeable by the user, remembered, and the `lang` attribute is set on pages for screen readers and SEO.
- [ ] 🟡 LOC-006 **Machine-translated text reviewed** by a fluent speaker for key flows (sign-up, payment, legal).
- [ ] 🟢 LOC-007 **SEO for languages:** separate URLs per language and `hreflang` tags (see `launch-ux.md`).

## Layout and text
- [ ] 🔴 LOC-008 **Scripts render correctly:** non-Latin scripts (Hindi, Tamil, Arabic, Chinese and others) display with suitable fonts, with no boxes (tofu) or broken characters in UI, PDFs, emails and exports.
- [ ] 🟡 LOC-009 **Right-to-left languages** (Arabic, Hebrew, Urdu) mirror the layout correctly if supported (`dir="rtl"`, logical CSS properties).
- [ ] 🟡 LOC-010 **Longer text fits:** layouts handle translations that are 30–50% longer than English (German, Tamil) without overflow or cut-off buttons.
- [ ] 🟡 LOC-011 **Search, sorting and validation** work for non-English text (accents, case, local sorting order, names that don't fit "first name / last name").

## Formats and regional rules
- [ ] 🔴 LOC-012 **Prices and currencies are right:** the correct currency and symbol, local number format (e.g. 1,00,000 in India and 100.000,00 in Germany), and taxes shown the way each region expects (prices with or without VAT/GST).
- [ ] 🟡 LOC-013 **Dates, times and time zones** are shown in the user's format and time zone (see `functional-qa.md`).
- [ ] 🟡 LOC-014 **Phone numbers and addresses** accept international formats (E.164 for phones), with no US-only fields like "State" or "ZIP" made mandatory for everyone.
- [ ] 🟡 LOC-015 **Units** (metric or imperial, sizes) suit the region if the app shows them.
- [ ] 🟡 LOC-016 **Payment methods** fit each region (UPI in India, iDEAL in the Netherlands, local cards), if the app sells there.
- [ ] 🟢 LOC-017 **Regional content and features** that are restricted or different per country (age limits, banned products, data residency) are handled.
